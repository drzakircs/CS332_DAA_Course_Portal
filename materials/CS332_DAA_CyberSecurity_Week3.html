Session 7

Analysis Fundamentals

Input size · basic operation · running time · space complexity · counting operations

What to count?How to count?Why it matters?
Concept

Algorithm analysis estimates resource growth

Instead of asking only:

“How many seconds did it take on my laptop?”

Wall-clock time changes with hardware, compiler, language, and system load.

We ask:

“How does the work grow as n grows?”

This gives a machine-independent way to reason about scalability.

Visual model

The analysis workflow

1. Define input sizeWhat does n represent?
2. Choose operationWhat basic step dominates?
3. Count workHow often does it execute?
4. Express functionT(n), S(n)
5. Simplify growthFocus on dominant behavior
Use the repeated structure across the week. Students should apply these five questions to every code fragment.
Instructor + student guide

The five questions students should always ask

Before writing T(n)

  • What is the input?
  • What does n measure?
  • Which operation dominates?
  • How many times does it execute?
  • What extra memory is used?

Mini example

Problem: scan log entries for a suspicious IP.

Input size: n = number of log entries.

Basic operation: compare current IP with suspicious IP.

Cost: one comparison per log → Θ(n).

Teaching tip: Never allow students to jump directly to Big-O. First force them to identify n and the basic operation.

Basic operation

What operation should we count?

Definition

A basic operation is the dominant operation whose frequency best represents the running time.

Examples: comparisons, assignments, hash lookups, relaxations, character comparisons.

Cybersecurity example

In malware signature matching, the basic operation may be a pattern comparison or hash lookup.

In graph attack-path analysis, it may be examining an edge.

Counting operations

Single loop: linear growth

count = 0 for each log in logs: if suspicious(log): count = count + 1

Counting idea

If there are n logs, the suspicious check executes n times.

T(n) = an + b Growth: Θ(n)
Counting operations

Nested loops: quadratic growth

for each alert in alerts: for each rule in rules: compare(alert, rule)

Counting idea

If alerts = n and rules = n, the comparison may execute:

n × n = n² Growth: Θ(n²)

If alerts and rules are different sizes, use m × n.

Session 8

Best, Worst, and Average Case

The same algorithm can behave very differently on different inputs of the same size.

Concept

Same n, different input arrangement

✅

Best Case

Input arrangement that gives the lowest cost.

❌

Worst Case

Input arrangement that gives the highest cost.

⚖️

Average / Expected

Expected cost over a distribution of inputs.

Key idea: cases are not about small vs large n. They are about input arrangement or input condition for the same n.

Common misconception

Average case is not “half of the worst case” automatically

Average case requires a model

We need an assumption about how inputs are distributed.

For Linear Search, if target positions are equally likely, expected comparisons are roughly (n+1)/2 when present.

Expected behavior

In many algorithm discussions, average case means expected cost over a defined input distribution.

Always ask: average over what kind of input?

Interactive average-case intuition

Average comparisons for successful Linear Search

If the target is equally likely to be at any position from 1 to n:

Average = (1 + 2 + … + n) / n = (n + 1) / 2

Growth of Functions

From exact counts to complexity classes

O(1)O(log n)O(n)O(n log n)O(n²)O(2ⁿ)
Motivation

Small inputs hide bad growth

At n = 10

Many algorithms look acceptable.

10² = 100

At n = 1,000,000

Growth rate dominates implementation details.

n² = 10¹²

Security scale: a method that works for 100 log entries may fail for millions of events per hour.

Exit check

Final self-check questions

Q1
What is the difference between input size and basic operation?
↻
Answer
Input size defines the scale of the problem. Basic operation is the dominant action we count to estimate running time.
↻
Q2
Why is worst-case analysis useful in cyber security?
↻
Answer
Security systems must remain reliable under difficult inputs, attacks, heavy traffic, and adversarial conditions.
↻
Q3
Why is O(log n) usually better than O(n)?
↻
Answer
Logarithmic growth increases very slowly because each step greatly reduces the remaining search space.
↻
Q4
Why does n² become dangerous at large scale?
↻
Answer
Doubling n roughly quadruples the work. At millions of inputs, pairwise comparison can become operationally infeasible.
↻
